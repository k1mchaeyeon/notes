약 55초

슬라이드 12 · Route 53 · CloudFront · WAF

  1. 사용자가 assac.cloud를 입력하면 Route 53이 CloudFront로 안내하고, CloudFront가 ACM 인증서로 HTTPS를 처리합니다.
  2. CloudFront에는 WAF를 연결해서, 요청이 VPC에 들어오기 전에 먼저 검사하도록 했습니다.
  3. WAF 규칙은 세 가지입니다. 일반적인 웹 공격을 막는 규칙, SQL Injection을 막는 규칙, 그리고 같은 IP에서 5분에 1,000번을 넘게 요청하면 막는 규칙입니다.
  4. WAF를 통과한 요청만 origin.assac.cloud를 통해 WEB ALB로 전달됩니다.
  5. WAF를 거치지 않고 ALB로 바로 들어오는 경로를 막기 위해, WEB ALB는 CloudFront에서 오는 요청만 받도록 보안그룹으로 제한했습니다.
  6. CloudFront에서 WEB ALB로 가는 통신도 HTTPS로 암호화했습니다. CloudFront용 인증서는 버지니아 리전에만 둘 수 있어서, WEB ALB에는 서울 리전에서 인증서를 하나 더 발급해 연결했습니다.
약 30초

슬라이드 13 · 알람 · ASG 이벤트 · WAF 차단 로그

  1. 이상이 생기면 담당자가 바로 알 수 있도록 알림을 연결했습니다.
  2. 알리는 상황은 네 가지입니다. CPU나 오류 같은 지표가 기준을 넘었을 때, 서버가 새로 생기거나 종료될 때, WAF가 요청을 차단했을 때, 그리고 GuardDuty가 위협을 탐지했을 때입니다.
  3. 네 가지 모두 Lambda가 내용을 정리해서 Discord로 보냅니다.
  4. 실제로 SQL Injection 차단 알림과 서버 증감 알림이 Discord에 오는 것까지 확인했습니다.

항목별 근거

왜 IGW가 public 서브넷에만 영향을 주나

IGW 자체는 VPC 전체에 붙지만, 실제로 어느 서브넷이 인터넷에 나갈 수 있는지는 라우팅 테이블이 결정해요. public 라우팅 테이블만 "0.0.0.0/0 → IGW" 경로를 갖고 있고, was·db 라우팅 테이블엔 이 경로가 없어서, IGW가 있어도 private 서브넷은 여전히 인터넷과 직접 통신할 수 없어요.
